# 05 · 实现复盘与后续方向

本记录基于本次实际实现与验证，不冒充用户个人学习经历。

## 最难的问题：失败本身也需要证据

工具失败时，Agent 能正确说“无法核验”，但初始审核器只看到空文档列表，看不到工具错误。它把正确的故障声明当成无依据回答，导致反复修正。这说明审核上下文必须包含业务证据与执行证据两类信息。

修复方式是把工具观察传给审核器，并明确工具失败无须企业制度引用。进一步修改评估：失败场景必须正常结束为 incomplete，不能因预算耗尽而通过同名状态断言。这比只检查最终状态更能发现真实缺陷。

## 检索经验

复杂度不高的中文 BM25/字符检索也有边界：短查询只有一个词项，固定重叠阈值会直接漏检。先用可解释本地检索，再用真实改写样例验证，比先引入向量数据库更适合本题的小规模交付。

## Agent 与固定流程的边界

图结构固定不等于决策固定。真实循环中的查询词、文档选择、补查、停止都由模型结合观察决定；代码负责允许的动作、校验与预算。Mock 可以帮助验证执行器，但无法证明模型会选择合适动作，必须保留分离的真实证据。

## 交付经验

结果必须可追溯到当时的资料版本，否则文档更新会使旧引用失真。快照、原文位置、实际 Trace 与上下文前置运行一起保存，才能复核“答案为什么变化”。

界面测试也要覆盖用户可见控件和小屏入口，类型检查通过不保证交互可用。

## 下一步

1. 建立人工标注的更多制度冲突与范围限定用例，统计多次运行稳定性。
2. 比较关键词基线与本地多语言 Embedding 的召回提升，记录成本及误召回。
3. 加入明确的制度替代关系、部门权限和有效期元数据，并用证据验证冲突是否可解决。
4. 使用独立审核模型或人工抽检减少生成与审核的共同偏差。
5. 若扩展到生产，补充认证、授权、任务队列、重启续跑与文档治理；不把本机演示服务直接暴露到公网。
